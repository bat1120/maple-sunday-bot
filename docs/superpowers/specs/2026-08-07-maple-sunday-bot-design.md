# 썬데이 메이플 공지 알림 봇 — 설계

작성일: 2026-08-07

## 목적

메이플스토리 "썬데이 메이플" 공지가 올라오면 디스코드 채널에 알림을 보낸다.
공지를 매번 직접 확인하지 않아도 혜택 내용을 디스코드에서 바로 보게 하는 것이 목표다.

## 범위

**포함**
- 썬데이 메이플 이벤트 공지 감지
- 디스코드 채널 1개로 알림 발송 (제목 + 링크 + 이벤트 기간 + 본문 이미지 전체)
- 중복 발송 방지

**제외 (YAGNI)**
- 슬래시 커맨드 (`/썬데이` 등)
- 여러 서버 / 여러 채널 지원
- 이미지 내용 요약 (혜택은 이미지 원본으로 확인)
- 일요일 당일 리마인드
- 썬데이 외 공지(업데이트, 캐시샵, 점검 등)

## 확인된 사실

브레인스토밍 중 실제로 검증한 내용:

- 썬데이 메이플은 **공지사항이 아니라 이벤트 게시판**에 올라온다.
  예: `https://maplestory.nexon.com/News/Event/1356`
- 이벤트 본문의 혜택 내용은 **전부 이미지**다. 파싱할 텍스트가 없다.
  이미지 호스트 패턴: `https://file.nexon.com/NxFile/download/FileDownloader.aspx?oidFile=...`
- 넥슨 오픈 API에 이벤트 공지 목록/상세 엔드포인트가 존재한다.
  - Base URL: `https://open.api.nexon.com`
  - 인증: 헤더 `x-nxopen-api-key`
  - 목록: `GET /maplestory/v1/notice-event` (응답에 `notice_id` 포함)
  - 상세: `GET /maplestory/v1/notice-event/detail?notice_id=...`
  - 호출량 초과 시 `429` / 에러코드 `OPENAPI00007`
- 제목 표기가 "썬데이 메이플", "스페셜 썬데이 메이플" 등으로 갈린다.

**구현 시 확인이 필요한 항목** — 목록/상세 응답의 정확한 필드명(`title`, `url`, `date`,
`date_event_start`, `date_event_end`, `contents` 등)은 API 키 발급 후 실제 호출로 확정한다.
확정한 응답은 테스트 fixture로 저장한다.

## 아키텍처

### 실행 방식

GitHub Actions의 `schedule` cron이 30분마다 스크립트를 1회 실행한다. 상주 프로세스가 없다.

이유: 채널 1개, 주 1회 이벤트, 슬래시 커맨드 불필요. 상주 봇이 필요한 요구사항이 없다.
서버 비용 0원이고 사용자 PC가 꺼져 있어도 동작한다.

리포지토리는 **public**, cron은 **30분 주기**로 확정한다. private일 경우 Actions 무료
사용량(월 2000분)에 30분 주기가 근접하기 때문이다. 시크릿은 GitHub Secrets에 저장하므로
public이어도 노출되지 않는다.

`workflow_dispatch`도 함께 걸어 수동 실행을 가능하게 한다.

**지연 특성**: GitHub cron은 러너 혼잡 시 지연될 수 있어 공지 게시부터 알림까지 최대 1시간 정도
걸릴 수 있다. 썬데이 공지는 통상 목~금에 게시되고 적용은 일요일이므로 허용 범위다.

### 파일 구조

```
maple-sunday-bot/
├─ .github/workflows/check.yml
├─ src/maple_sunday_bot/
│  ├─ nexon.py       # 넥슨 오픈 API 클라이언트
│  ├─ notice.py      # 썬데이 판별 + 본문 이미지 URL 추출
│  ├─ discord.py     # 웹훅 페이로드 조립 및 전송
│  ├─ state.py       # 발송 완료된 notice_id 읽기/쓰기
│  └─ main.py        # 진입점 (조립 + CLI 플래그)
├─ state/seen.json
├─ tests/
│  ├─ fixtures/      # 실제 API 응답 샘플
│  └─ test_*.py
├─ pyproject.toml
└─ README.md
```

언어는 Python, HTTP는 `requests`를 쓴다.

### 모듈 책임

| 모듈 | 하는 일 | 의존 |
|---|---|---|
| `nexon.py` | 이벤트 공지 목록/상세 조회. 재시도·에러 변환 담당 | `requests` |
| `notice.py` | 제목으로 썬데이 여부 판별, 본문 HTML에서 이미지 URL 추출 | 표준 라이브러리만 |
| `discord.py` | 공지 데이터 → 웹훅 페이로드 변환, 전송 | `requests` |
| `state.py` | `seen.json` 읽기/쓰기 | 표준 라이브러리만 |
| `main.py` | 위 넷을 조립. 어떤 순서로 무엇을 할지만 담당 | 위 전부 |

`notice.py`와 `state.py`는 네트워크에 닿지 않는 순수 로직이라 테스트가 쉽다.
`nexon.py`와 `discord.py`는 HTTP 경계를 한 곳에 몰아둔 얇은 층이다.

## 데이터 흐름

1. GitHub Actions가 `main.py`를 실행한다.
2. `nexon.get_event_notices()` → 이벤트 공지 목록.
3. `notice.is_sunday(title)`로 필터 + `state.load_seen()`에 없는 `notice_id`만 남긴다.
4. 남은 각 공지에 대해 `nexon.get_event_notice_detail(notice_id)` → 본문 HTML.
5. `notice.extract_images(html)` → 이미지 URL 리스트.
6. `discord.send(notice, images)` → 웹훅 전송.
7. 전송에 성공한 `notice_id`만 `state.add_seen()`으로 기록.
8. `seen.json`이 변경됐으면 Actions가 리포에 커밋·푸시한다.

### 썬데이 판별 규칙

제목을 공백 제거 후 소문자화하여 `"썬데이메이플"` 부분 문자열을 포함하는지 본다.
"썬데이 메이플", "스페셜 썬데이 메이플", "썬데이메이플" 모두 걸린다.

### 메시지 형태

디스코드 임베드는 하나당 이미지 1장만 표시되므로, 한 메시지에 임베드를 여러 개 담아
이미지를 전부 보여준다.

- 첫 번째 임베드: `title` = 공지 제목, `url` = 공지 링크, `description` = 이벤트 기간,
  `color` = 주황색, `image` = 첫 번째 이미지
- 이후 임베드: `image`만 채운 임베드를 이미지 개수만큼 추가

디스코드 제약상 한 메시지에 임베드는 최대 10개다. 이미지가 10장을 넘으면 메시지를 나눠 보낸다.

이미지가 하나도 없으면 제목 + 링크 + 기간만 담은 임베드를 보낸다.

## 상태 관리

`state/seen.json`에 발송 완료된 `notice_id` 배열을 저장한다.

```json
{ "seen": [1356, 1352, 1350] }
```

GitHub Actions가 실행 후 이 파일을 커밋해서 다음 실행이 이어받는다.
(부수 효과: 이 커밋이 리포 활동으로 잡혀, 비활동 60일 후 스케줄이 꺼지는 문제도 함께 막힌다.)

파일이 무한히 커지지 않도록 최근 100건만 유지한다.

### 첫 실행 처리

`seen.json`이 비어 있는 상태로 그냥 돌리면 과거 썬데이 공지가 한꺼번에 발송된다.
이를 막기 위해 `main.py`에 `--bootstrap` 플래그를 둔다.

- `--bootstrap`: 현재 목록의 썬데이 공지 `notice_id`를 전부 `seen.json`에 기록하고 **발송하지 않는다.**
- 최초 1회 로컬에서 이 플래그로 실행한 뒤 커밋하고, 이후 Actions는 플래그 없이 돈다.

## 에러 처리

| 상황 | 처리 |
|---|---|
| 목록 조회 실패 / 429 | 지수 백오프로 3회 재시도. 최종 실패 시 상태를 건드리지 않고 워크플로우를 실패로 종료 (다음 회차에 재시도) |
| 상세 조회 실패 | 해당 공지를 이미지 없이 제목 + 링크 + 기간만으로 발송. 알림 누락이 이미지 누락보다 나쁘다 |
| 디스코드 전송 실패 | 해당 `notice_id`를 `seen`에 넣지 않는다. 다음 회차에 다시 시도 |
| 이미지 여러 장 중 일부 실패 | 이미지 URL은 디스코드가 직접 가져가므로 봇 쪽 처리 없음 |
| 새 공지 없음 | 아무것도 안 하고 성공 종료 (커밋도 없음) |

기본 원칙: **디스코드 전송이 성공한 직후에만 `seen`에 기록한다.**
전송 전에 기록하면 전송 실패 시 공지를 영영 놓치고, 너무 늦게 기록하면 중복 발송이 난다.

이 원칙에도 남는 구멍이 하나 있다 — 전송은 성공했는데 그 뒤 커밋·푸시가 실패하면 다음 회차에
같은 공지가 한 번 더 간다. 주 1회 이벤트에서 드물게 알림이 두 번 오는 정도는 감수한다.
이를 막겠다고 트랜잭션을 만들 가치는 없다.

## 설정

GitHub Secrets 두 개만 필요하다.

| 이름 | 획득처 |
|---|---|
| `NEXON_API_KEY` | openapi.nexon.com 로그인 후 애플리케이션 등록 (무료) |
| `DISCORD_WEBHOOK_URL` | 디스코드 채널 설정 → 연동 → 웹훅 생성 |

로컬 실행 시에는 같은 이름의 환경변수를 쓴다. 둘 중 하나라도 없으면 즉시 명확한 에러로 종료한다.

## 테스트

`pytest`. 네트워크를 타지 않는다 — 실제 API 응답을 `tests/fixtures/`에 JSON으로 저장해 쓴다.

| 대상 | 검증 내용 |
|---|---|
| `notice.is_sunday` | "썬데이 메이플", "스페셜 썬데이 메이플", "썬데이메이플" 통과 / "썬데이" 없는 이벤트 제목 탈락 |
| `notice.extract_images` | fixture HTML에서 이미지 URL 전부 추출, 이미지 없는 본문은 빈 리스트 |
| `state` | 저장/로드 왕복, 파일 없을 때 빈 상태, 100건 초과 시 잘림 |
| `discord` 페이로드 조립 | 이미지 0장/1장/12장에 대한 임베드 개수와 메시지 분할 |
| `nexon` 재시도 | 429 응답 시 재시도 후 성공, 3회 실패 시 예외 |
| `main` 통합 | fixture 기반으로 목록→필터→발송→기록 전체 경로. 이미 본 공지는 발송 안 됨 |

수동 검증: API 키·웹훅 설정 후 `workflow_dispatch`로 1회 실행해 실제 디스코드 메시지를 확인한다.

## 완료 기준

- 새 썬데이 공지가 올라오면 30분~1시간 내에 디스코드 채널에 제목·링크·기간·이미지 전체가 도착한다.
- 같은 공지가 두 번 발송되지 않는다.
- 넥슨 API가 죽어 있어도 봇이 조용히 실패하고 다음 회차에 정상 복구된다.
- 사용자는 Secrets 두 개만 넣으면 된다.
